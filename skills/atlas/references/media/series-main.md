# 系列主文与合集条目

## 0. 先判层级（判错，整篇范围就错）

| 层级 | 对象 | 这一页负责 | 这一页不写 |
|---|---|---|---|
| **IP 级** | 一个完整 IP 或品牌 | 起源、创作史、介质版图、子系列索引、跨层关系、入门顺序 | 单作完整剧情、逐卷书目、完整 staff、子系列内部细史 |
| **子系列 / 企划级** | IP 下一条有独立概念、共享世界观或共同企划的分支 | 与父 IP 的边界、企划沿革、共享世界观、作品构成与计划演变、旗下索引 | 不属于本分支的载体、单作完整剧情 |
| **合集条目** | **同一系列的多代编号作品**，且要求合写一篇 | 见 §4 | 逐代完整剧情 |

容易搞混的三种东西：

- **载体条目**（一部具体作品）→ 走 `wiki-skeleton` + 一个 `media-*`。
- **作品级简介**：一个复杂单作的可选总览（服务多个版本或路线）→ **不是主文**，也不替代载体正文。
- **专题资料**：时代、技术史、访谈整理、世界观资料 → 跨多个对象时**独立成文**，不硬塞进主文。

**层级不是越多越好**：只有读者需要区分范围、顺序或关系时才加一层。

## 1. 动笔前先画对象树

从可靠来源列出：父 IP → 子系列 / 企划 → 独立作品 / 版本。给每个对象标四项：

1. 是不是独立发行单元；
2. 与其他对象是改编、续作、重制、衍生、共享世界观，还是仅再发行；
3. 当前有没有正文；
4. 需要独立条目，还是主文里一行带过。

**已有条目的数量只说明建设进度，不能证明这个 IP 只有一种介质。** 不要把宣传短片、周边商品、普通外站页面当成载体。

## 2. 信息分配：同一事实只在一层展开

| 事实 | 归哪一层 |
|---|---|
| 单作的版本、设定、完整剧情、机制、角色、评价 | **载体条目** |
| IP 起源、创作史、介质版图、子系列索引 | 父 IP 主文 |
| 分支的背景、共享规则、企划构成与演变 | 子系列主文 |
| 同一部作品两层都要提 | 父页写**定位和索引**，子页写**它在本分支里的作用** |

主文可以很详细，但"详细"指**增加可核查的历史、关系、设定和因果**，不是把每部作品的剧情段落重复一遍。

**主文同样不回避剧透**：系列主线、企划神话、关键转折和结局，只要是理解本层级所必需的就完整写。限制来自**对象范围**，不是"不能剧透"。

## 3. 两个骨架模板

**IP 级**：标题 `# <IP 名称> 系列索引`

```markdown
> 说明：本文范围、主要来源、资料截止日期、必要的剧透提示

## 作品概览
## 创作与发展（有足够史料时）
## 核心设定与系列主题（确有跨作内容时）
## 子系列与载体索引
### 游戏 / ### 影视动画 / ### 漫画小说
## 时间线与关系
## 阅读、观看或游玩顺序
## 其他载体或待建对象
## 事实来源
```

- 首段一段话完成定位：名称与可核实别名、创作者或推出方、起点、核心故事或主题、主要扩展方向；末句声明「本页负责总览，单篇条目只讲自身」。
- **首段不放某个版本的片长、卷数、ISBN、平台细节或未核实的销量。**
- 概览按「起源 → 核心概念 → 介质与阶段」展开，不展开单篇发行细节。
- 载体索引每行：对象名称 + 载体 + 关键日期（有来源才写）+ 一句定位；**已完成与待建要能区分**。
- 时间线与关系只写**跨对象的接口和顺序**，具体差异回到各载体条目。
- 顺序有多条路线时分路线写，**不硬给唯一答案**。

**子系列 / 企划级**：同一体裁，范围收窄

```markdown
> 说明：与父 IP 的关系、本文范围、主要来源、资料截止日期

## 子系列定位
## 创作背景与企划沿革
## 共享世界观与核心设定（适用时）
## 作品构成与计划演变
## 旗下作品索引
## 时间线、关系与顺序
## 与父 IP 及其他分支的接口
## 事实来源
```

- **子系列定位**：属于哪个父 IP、共享什么、又独立什么。
- **创作背景与企划沿革**：概念提出 → 正式公布 → 开发调整 → 最终落地。
- **共享世界观**：只在这个框架是读者理解本分支所必需时才写；每个断言要有来源，或明确标为推断。

## 4. 合集条目（多代合写一篇）

**什么时候用**：用户明确要求合并（"把这一系列各代合成一篇"），或各代体量有限、单独成篇会稀薄；且各代共用同一套核心机制 / 世界观，差异集中在版本迭代上。
**判断依据是任务要求 + 材料体量，不是作品数量**——材料足够、各代叙事彼此独立时，仍应逐代建档。

**另一种情形：对象是一个"真实存在的合集产品"**（厂商把之前几代打包装在一起卖，如《光环：士官长合集》）。那不是"我们选择合写"，而是**一个独立发行的产品**——走**载体条目**（`wiki-skeleton` + 一个 `media-*`），只是第 4 章**按代次分节**、2.2 写清它包含哪几代与各代改了什么（本节下面的骨架改法可以直接借用）。**各代若另有独立条目，本条目只写接口、不搬它们的剧情。**

**骨架怎么改**（仍用 `wiki-skeleton` 的骨架与对应介质章名）：

- 标题写 `# <系列名> 系列合并 Wiki`；
- 第 1 章写**系列整体定位 + 分段演化**，不逐代复述剧情；
- 在 2.x 增加一节**主干作品脉络**：按时间列各代，每行「名称（年份）：一句定位」；
- 2.2 扩成**各代之间的关系与迭代**：哪代是重制 / 复刻 / 重启，哪些是正传编号；
- 第 4 章**按代次分节**（每代一节），每节只写该代主线与代表转折；
- 第 5、6 章写**跨代的机制与角色演化**：共同机制只讲一次，各代差异点出；
- 第 7 章按**系列史**写，不落到单作评价。

**硬规则**：

- 每条事实都要落到**具体哪一代**——不能用"这个系列一直……"糊过去；
- 不把任意一代的剧情当成整个系列的剧情；
- 体量上限相应放宽，但增加必须是**事实与结构**，不是重复；
- 交付说明里写清**覆盖了哪几代、哪些代因材料不足略写**。

## 5. 「计划中」的状态要分开写

| 状态 | 写法 |
|---|---|
| 计划中 / 概念阶段 | 写明这是计划，附公布时间与来源 |
| 已正式公布 | 公布日期 + 当时给出的信息 |
| 已发售 / 已播出 | 实际日期 + 载体 |
| 改名、转型、延期 | 旧名 → 新名 + 变更时间 + 依据 |
| 取消、脱离企划 | 写明何时、依据什么判断脱离 |

**不要把宣传阶段的阵容当成实际系列。**

## 6. 事实与引用（在主文里加码的两条）

- 「计划 / 公布 / 开发中 / 发售 / 重命名 / 取消 / 脱离企划」是**七种不同状态**，按来源和时间分别写，**不能合并成一句**；
- 索引行若**直接取自已有条目、没有独立复核** → 在交付记录里标明「取自条目，未独立复核」，**不要把旧条目自动升级成已核实事实**。

## 7. 失败路径（On Failure）

- **层级判不准**（这是 IP 主文，还是一个复杂单作的总览？）→ **先确认**；判错范围，整篇都要重来。
- **对象树画不完整**（不知道有哪些分支 / 版本）→ 先列已确认的，其余标「待建 / 待核实」；**不要为了把索引补满而猜**。
- **只是"看起来像系列"**（几部作品共用角色，但不是同一企划）→ **不硬合并**：按载体各自成篇，关系用边表达。
- **材料只够写索引** → 就写索引体量，**不要**用单作剧情把主文撑长。

## 8. 自检（每项不通过 → 回哪一步）

1. 标题与首段准确表明层级，父 IP 与子系列没有混写？→ 混了：回 §0。
2. 首段只有系列级定位，没有单载体的发行细节？→ 有：回 §3。
3. 概览讲跨作品脉络，没有重复索引行里的完整事实？→ 有：回 §2。
4. 每个索引行的名称都唯一指向一个实际对象，计划状态与发行状态没有混淆？→ 有：回 §5。
5. 没有把某部作品的完整剧情、逐卷书目或完整 cast 压缩进来？→ 有：回 §2。
6. 时间、销量、奖项、现状都带来源、口径与检索日期？→ 缺：回 `fact-check`。
7. 合集条目里每条事实都落到具体哪一代了？→ 没有：回 §4。
