# 进料分析

**这是"两步式进料"的第一步**：先分析、再生成。它**只做判断、不动库**——建档与挂链是人的动作，它产出的是**建议**。

> 例子都是示范，不是模板。

## 1. 输入 / 输出

```
Input:
  entry        库条目（source + externalId + 标题 / 年份 / 容器 / 封面）或目标节点 id
  libraryState 库里已有的相关候选（系统预取：同名 / 别名命中 / 同级单作 / 容器系列 / 关系边）

Output:
  identity     这是**什么**（作品 / 版本 / 载体：game|movie|tv|manga|book）+ 判定依据
  relations[]  与库里哪些节点有关（节点 id + 关系类型 + 依据）——**只写能被引用或材料支撑的**
  conflicts[]  与现有内容的矛盾或张力（同一段故事被别的作品讲过？版本冲突？）
  placement    建议怎么建（建在哪个节点下 / 要不要并入已有节点 / 归入哪个系列）
  actions[]    建议动作（**枚举**：建档 / 关联 / 合并 / 研究 / 忽略）+ 一句理由
  questions[]  材料不足时列出的待查问题（**宁缺勿猜**）
```

## 2. 规则

1. **先定对象边界**：这是"一部作品"，还是"某作品的某个版本 / 某季 / 资料片"？边界判错，后面全错。
2. **候选要去重**：同一部作品在库里可能同时存在系列节点与单作节点——列全，别只报一个。
3. **结论必须带依据**：依据来自库内已有内容或材料；**没有依据就不写**（不要写"感觉像"）。
4. **不发明事实**：拿不准的一律进 `questions`，不要猜。
5. **动作只给枚举值**，并且**只建议、不执行**（建档 / 挂链由人确认）。
6. 分析**未建档的库条目**是允许的——它的作用正是"该不该建、建到哪"。

## 3. 失败路径（On Failure）

- **条目信息不足**（只有标题）→ 先检索；仍不足 → `identity` 标「待定」+ 把要查的写进 `questions`，**不要硬判**。
- **库里没有相关候选** → `relations` 留空即可，**不要硬凑"相似"关系**。
- **命中多个候选（同名 / 同系列多节点）** → **全列出来** + 标注「需人裁决」，不要自己选一个。
- **与现有内容矛盾** → 写进 `conflicts`，**不要顺手去改已有正文**（那是 `revise` 的事）。
- **判定与系统预取不一致**（预取说同级、你认为不是）→ 两个都写出来，注明分歧，交给人。

## 4. 自检（每项不通过 → 回哪一步）

1. 对象边界定了吗（一部作品 / 一个版本）？→ 没有：回 §2.1。
2. 相关候选列全了、去重了？→ 没有：回 §2.2 + §3。
3. 每条结论都有依据、或明确标了「待查」？→ 没有：回 §2.3–2.4。
4. 动作是枚举值、且没被执行？→ 不是：回 §2.5。
5. 有没有顺手改库（建节点 / 挂链 / 改正文）？→ 有：撤掉，回到 §2.5。
6. 拿不准的进了 `questions`，而不是被猜成结论？→ 没有：回 §2.4。
