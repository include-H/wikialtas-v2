# WikiAtlas v2 · 技能（Skill）体系设计

> 功能见 `docs/features.md`；AI 能力面见 `docs/ai.md`；**提示词/质量门**见 `docs/prompts.md`；**行为知识（技能段只放 L0 目录的来由）**见 `docs/behavior-notes.md §6`；外部参考见 `docs/refs/trae-skill-best-practice.md`。本文件只管**技能怎么组织、怎么加载、怎么写**。
> **已定**：「写得好」的定义 = **18 篇成品**（按 `游戏 / 影视 / 书籍` 三组）（放在 `skills/samples/`，下称"基准语料"）。但**「写得好」指的是正文整体质量、信息密度在同一水平，不是每一处细节都无瑕**。

## 0. 为什么要重写，而不是在 v1 的 skill 上缝补

v1 的实际做法（读代码得到）：`FilesForIntent(intent, medium, nodeKind)` 把 `SKILL.md` + `core.md` + `media-*.md` **强塞进 system prompt**，每个工单都塞（单文件上限 9000 runes、总计 20000）。

三个后果：

| 后果 | 表现 |
|---|---|
| **噪音** | 写第 4 章剧情时，上下文里也躺着题记的 60 行规则、图书的卷册规则 |
| **过拟合** | `core.md` 里混进大量"针对某次失败的特判"（`不要写「最后真相大白」`、`不要用「据说」`…），越改越像补丁；近 600 行里挑不出哪条是结构契约、哪条是一次教训 |
| **耦合** | 改一句 `core.md` 影响所有工单，且没有局部验证手段 |

**v2 的两条修正**：

1. **目录常驻、正文按需**（渐进式发现，即 Claude Code / Codex / Command Code 那种加载方式）。
2. **能机械校验的规则，一律搬进质量门（代码），技能只留"判断"。** 核心判据：**每条规则都要能回答"删了它会坏什么"**；答不出的删掉。

## 1. 四层结构（三层技能 + 一层资源）

```
L0 目录（常驻 system prompt，目标 < 60 行）
   每个技能：name · 一句话 description · 何时用 / 何时不用
        ↓ 模型按任务决定读什么
L1 技能正文（单文件，按需 load；≤500 行）
        ↓ 只在需要细节时
L2 细则（可选，按需深读；>100 行的细则文件顶部加目录）
L3 资源 = skills/samples/ 的基准语料（`游戏/` `影视/` `书籍/` 三组共 18 篇）（模型按需读，只读相关一节）
```

- **加载协议**：`list_skills`（L0 目录由各技能的 frontmatter 扫出来）+ `read_skill(name, section?)`；`/skill` 显式指定能覆盖模型的选择。
- **触发由任务决定，不由页面决定**。v1 是"到了写作页就强加载"；v2 是"模型在做这件事时才去读这件事的规则"。
- **`description` 必须写清"何时用 / 何时不用"**——借 llm_wiki 的触发纪律（它明确声明"不因泛泛的『搜我的笔记』触发"）。
- **资源层（`skills/samples/`）**：技能里写 `sample:<文件名>` 就是让模型去读它；**必须写明"只读哪一节、不要整篇照抄"**。样例没有 frontmatter，不会被当技能扫到。
- **引用只一层**：技能之间避免 A→B→C 链式引用（模型可能只读到一部分）。
- 机制细节：`read_skill` 要**路径穿越防护**（v1 有）+ **大文件截断要说话**（别静默截）。

## 2. 技能粒度：从"意图 × 介质"改为"任务阶段"

**14 个技能已全部写完**（`skills/README.md` 是 L0 目录的真身）：

| 技能 | 何时读 | 承载 | 状态 |
|---|---|---|---|
| `wiki-write` | 任何写正文 | 交付物四类 · 完整建档 / 增量编辑两个模式 · 开写前四问 · 六条硬规则 | **已写** |
| `wiki-skeleton` | 写整篇 | 章节骨架（含可选的「名台词与名场面」）· 章名按介质替换（**三档**）· 小节编号 · 字段行 · 排版 | **已写** |
| `epigraph` | **只在写题记时** | 先找材料（**台词优先**）再定写法（引用 / 场景 / 诗句）· 署名 · 剩余名句的去处 · 禁区 | **已写** |
| `prose-style` | 通篇润色 / 收尾 | 具体化 · 禁套话 · 事实推断评价分开 · 改前→改后 | **已写** |
| `fact-check` | 写字段/剧情/评价 | 来源分层 · 三档强度 · 缺口三处理 · 事实账本 | **已写** |
| `multi-source` | 同一段故事被多部作品讲过 | 先划本作边界 · 两边都写并标出处 · 跨作品问答要连带 | **已写** |
| `media-game` / `media-video` / `media-book` | 按介质读**一个** | 介质差异（章名之外的所有写法） | **已写** |
| `series-main` | 节点是 series / universe | 层级判定 · 两个骨架模板 · 合集条目 · 计划五态 | **已写** |
| `index-fields` | 要写/改别名、标签、关系、介质字段时 | 索引层字段的判断（别名只收指向本对象的名称 · 关系要具体且方向按契约 · 结构动作不夹在润色里） | **已写** |
| `analyze` | 分析库条目或待建档对象时 | 结构化结论：这是什么 / 与谁有关 / 矛盾 / 建议怎么建（**枚举动作、不动库**） | **已写** |
| `qa` | 用户就库内容提问时 | 只据库内容 · 引用到节点 · **库里没有就说没有** · 好答案可存成资料 | **已写** |
| `revise` | 用户要求改已有正文的某一部分时 | 只动指定范围 · 输出只含替换片段 · 给理由 | **已写** |

**按需加载最值钱的一刀**：`epigraph` 在 v1 是每次写正文都带着的 60 行，而题记**通篇只写一次**。

## 3. 写法规范（"反过拟合"的操作定义）

1. **每条规则要能回答"删了它会坏什么"**；答不出 → 删。
2. **禁止特判**（"上次模型把 X 写成 Y，所以别 Y"）。这类内容分两路消化：
   - **可机械校验的** → 搬进**质量门**（代码）：章节齐全 · 编号连续 · 字段行格式 · `:::epigraph` 唯一 · 参考资料条数 · `待核实` 的用法 · 禁用表达
   - **不可机械校验的** → 留在技能里，写成准则 + 正反例
3. **不许写"不存在的禁忌"。** 规则只能来自三处：**① 基准样例 · ② 真实失败 · ③ 用户的明确要求**。
   > 反例：写过"不设 `## 引言`"——而"引言"从未在任何一篇里出现过。**凭空引入一个概念再禁止它 = 纯噪音**，已删。
4. **教判断，不教长相。** 技能要教"按手上的材料做选择"，而不是规定"必须长什么样"。
   > 例：题记的写法由材料决定——能引到台词就引台词、能引到歌词就引歌词、引不到就写场景。
5. **不许从单个实例推断类别规则。** 这是过拟合最常见的形态：把"某部作品碰巧如此"写成"这类作品应当如此"。
   > 反例：因为 `16bit的感动` 有一个点睛的 ED，就把"动画 / 游戏 → 歌词"写成材料指引；真实情况是**台词才是最常见的来源**。
6. **例子是示范，不是模板。** 每个技能顶部标一次这句话；例子能短则短；完整示例**指向 `sample:` 资源，不抄进技能**。
7. **清单要问"最常见的那一项在不在"。** 枚举类内容（材料类型、字段、动作）漏掉最常见的一项，比多写两项更糟。
   > 反例：`epigraph` 的材料清单一开始把"**台词**"漏成了只讲歌词与诗。
8. **技能里只放两样东西：给模型的指令 + 可读的正面范例指针。**
   **维护者元信息一律不进技能**（依据 · 置信度 · 基准瑕疵 · 历史 · 待定）→ 全部放 `docs/`。
   > 反例 1（悬空指针）：写过"示范：`007：初露锋芒`"，而当时运行时的技能语料里并没有那一篇 → 模型拿不到，只能脑补。
   > 反例 2（自相矛盾）：写过"基准里 `上古卷轴_V_天际` 那句没署名是处小败笔"——**把基准的瑕疵告诉模型，等于告诉它"必须署名"这条规则可以破**；规则与基准打架时，模型会挑对自己有利的那边。
9. **技能不写宿主/接口/数据库/目录/审批**——那些归工具描述与系统提示。
   > 推论：**契约类的东西（枚举、方向语义、字段约束）在代码层一处定义**，技能只说"按契约填"。见 §6 的 `frontmatter.md` 拆分。
10. 每个技能配**正反例**；不许只写"要具体"这种空话。
11. 技能要能**单独验证**：改一个技能只跑它相关的评测用例与质检项（见 §5）。
12. **失败路径要写（On Failure）**：每个技能都要交代"失败 / 不适用时怎么办"，别让模型自由发挥。
13. **有产出物的技能要写结构化 Input / Output**（函数签名式：字段 + 类型 + 含义）。适用于 `analyze` / `qa` / `revise` 这类"要交出一份东西"的技能。
14. **必须给默认路径**：存在多种做法时指明**默认 + 例外条件**；**禁止罗列等价选项**。
15. **技能里不写时效性信息**（日期、版本号、"某年之前的做法"）。
16. **自检要带闭环**：每条检查不通过时写明**回到哪一步**，不是只列检查项。
17. **按脆弱度选指导方式**：脆弱 / 要求一致 / **必须按序列**的环节 → 给**固定契约**（能落到质量门就落质量门）；存在多种合理做法时 → **只给原则**。

## 4. 降低"模型自己问"的比例：结构化用户输入

借 llm_wiki 的**技能交互表单**：技能声明它需要哪些输入（单选 / 多选 / 自由文本），宿主渲染成 AntD 表单。

用途：剧透偏好 · 深度（完整 / 只补某章 / 概览）· 介质判定 · 是否联网核实。

**替代 v1 的做法**——v1 把"开写前的四个确认"写在 `core.md` 里让模型自己问（还不一定问）；v2 变成**确定性表单**：该问的必问，答案进工单上下文。

## 5. 校验与回归：以基准语料 + 评测用例为准

**基准语料 = 18 篇成品**，按介质分三组放在 `skills/samples/`（`sample:` 只写文件名，加载器递归找）（既是模型可读范例，也是回归与对齐的唯一依据）：

`007_初露锋芒` · `16bit的感动（TV动画）` · `风之谷（漫画）` · `上古卷轴_V_天际` · `仙剑奇侠传_1995` · `现代战争`

技能内容必须与基准**双向对齐**：

| 方向 | 判据 | 不合格怎么办 |
|---|---|---|
| **规则 → 样例** | 每条规则都能在基准里找到体现 | 找不到体现的规则 = **高危补丁**，删掉或降级为质量门告警 |
| **样例 → 规则** | 全部基准都满足规则 | 要么规则写错了，要么这篇不达标 → **回头问用户**（不许偷偷改样例） |

**两个活的例子（这条纪律确实在起作用）**：

1. 用户要求"题记只挑一句，其余名句另设一节收着"——这个章在当时那 6 篇里不存在，所以设计成**可选章**（有材料才出现、编号顺延），**当时的 6 篇因此仍然满足规则**。
2. 读全语料发现两处**规则写错**并已修：章名按介质替换其实是**三档**（影视=叙事与影像特色 / 图书=创作特色 / 游戏=玩法与结构特色，依据 `16bit`、`风之谷`、`上古卷轴` 三篇）；`epigraph` 的署名格式写死了《作品名》，而 `现代战争` 的「——麦克米兰上尉」证明**引本作可省**。

**介质覆盖**（已补齐）：**18 篇 = 游戏 6 · 影视 6（动画 2 / 电影 2 / 电视剧 2）· 书籍 6（漫画 3 / 小说 3）**。三个组与三份介质技能（`media-game` / `media-video` / `media-book`）一一对应。

> 历史记录：补之前是 **6 篇（4 游戏 / 1 漫画 / 1 动画）**，影视与书籍两类**只有规则、没有基准**——那正是这一轮扩样本的原因。

**维护者文档与运行时的分界**：缺陷日志、依据、置信度、待定 → `docs/`；技能里只留指令与 `sample:` 指针（§3.8）。

### 5.1 评测（借 TRAE 的"评测驱动、失败优先"）

**技能已全写完。已经用 4 个真实任务跑过一轮评测**（产物在 `eval/`）：

| 任务 | 考点 |
|---|---|
| 使命召唤：无限战争（游戏） | 系列一员但剧情独立 → `multi-source` 该不该读 |
| 仙剑奇侠传2（游戏） | 续作与前作的承接（同系列、不同故事） |
| 博物馆奇妙夜（电影） | **无基准介质**；"借角色之口引用的外来名句"（莎剧变体） |
| 你的名字。（小说） | **无基准介质**；**同源改编**（小说化）的方向与边界 |

**结论**：渐进式发现**基本有效**——4/4 都只读了 14 份里的相关 7–10 份，误触发都被 `when_not` 挡住了。但暴露 **8 条摩擦，已逐条修**：

1. **`multi-source` 的 `when`（"系列一员"）与 `description`（"同一段故事"）互相打架** → 收窄 `when`，并在正文写"只是同一系列不算"（**4/4 命中**）。
2. **`prose-style` 的 `when`（"润色 / 收尾"）与 `wiki-write` 把它列为通用收尾打架** → `when` 扩到"任何写或改正文"（**4/4 命中**）。
3. 标题格式：**`Wiki` 后缀当时 6 篇基准全有**（现 18/18 仍全有），骨架漏了 → 补 `（载体或年份限定）Wiki`（1 命中）。
4. 字段里不能放冲突值：`fact-check` 的"并列争议"与骨架"值里只有值"冲突 → 加**默认路径**（冲突进正文、检索时间进说明行）（3 命中）。
5. `epigraph` 缺"**借角色之口引用的外来名句**"（莎剧 / 古诗 / 经句）的处理 → 补：不要署给角色，改用原创或按外部引文署名原作者（1 命中）。
6. `multi-source` 缺"**同源改编**"（小说化 / 漫画化 / 重制）：不是两个叙述、不要写成两套 → 新增 §2.1（1 命中）。
7. **第 8 章的引文门槛**：`fact-check` 的"逐字台词"档对**拿不到正文**的小说不可能达标 → 门槛改指 `epigraph` 的"能指到出处"，拿不到原文只写名场面。
8. **计数错误**：README 与本文档写"16 个技能"，实际 **14 个**（1 命中）。
9. **题记的双语排布没有唯一写法**：`epigraph` 原来写了"也可整段引出（段间空行）"，于是出现"原文一整段 + 中文一整段"（用户指出：应当是**一行原文 + 该行的中文，逐行交替**）→ 已删掉这个等价选项、改成强制逐行交替，并在自检里加一条。**这是"禁止罗列等价选项"（§3.14）的又一个实例。**
10. **基准挪动会留下悬空引用**：把 3 篇移出 `samples/` 后，`epigraph` 里两处 `sample:风之谷…` / `sample:现代战争…` 变成指向不存在文件的指针 → 已改指现行基准（§3.8：技能里不许有悬空引用）。

**基准与规则的冲突（处理记录）**：

- 《仙剑奇侠传_1995》的题记是**自创四句诗**、按「结缘 → 比武招亲 → 锁妖塔 → 南诏」点到四处舞台——与 `epigraph` 的「不复述剧情」冲突。用户裁定：**保留自创诗这条路**（不能强求「必须引原作诗」，有的武侠游戏没有可引素材）→ 已**放宽诗句式**：允许点到关键舞台与事件，但**不写结局、不揭关键反转**（并把三式的剧情尺度写清）。
- 《仙剑奇侠传2》§2.1 收了 `Chinese Paladin 2` 作英文译名，而现实中有同名影视 → 与 `index-fields`「别名只收真的指向本对象的名称」冲突。用户裁定：**无所谓，保持现状**（规则与样例都不动）。

**这一轮的结果**：样本集 **6 → 18 篇**（三组各 6）。9 篇新写 + 1 篇重写（`上古卷轴V`）由 10 个子代理按技能产出，**机械门全过**（标题 `Wiki` 后缀 / 题记唯一且逐行交替 / 1–7 章齐全 / 章名按介质三档 / 关系简述 / `>` 说明行），旧版《上古卷轴》留档 `_retired-samples/`。**影视与书籍两类从此有了基准**——上一节记为"还欠"的缺口就此补上。

**还欠**：**可复现的评测用例集**（这轮是真实任务，不是用例）；以及各篇的已知薄弱处（无基准介质里最薄的都是第 5 章的分析，见 `skills/samples/README.md`）。

- **评测用例先行**：写或改技能前，先有 3–5 个**可复现**用例，每个写明"通过 / 失败"判定；**优先覆盖最易误用的场景**（该触发没触发、**不该触发却触发**）。
- **保留"无 Skill"基线**：同一任务不给技能跑一遍当对照。**加了技能若没有明显改善 → 该技能就该简化或删掉。**
- **任何修改都要过已有回归；评测不过时优先简化，而不是叠加新规则**（与 §3.1 是同一件事的两面）。
- **真实使用校准**：观察是否**非预期误触发**、是否**漏读参考文件**、是否**反复读同一段形成隐性依赖** → 它们都是新用例，回到上游。

| 手段 | 管什么 |
|---|---|
| **质量门（代码）** | 全部机械项。技能怎么改都不影响它——**这是把规则从提示词搬到代码的收益** |
| **快照测试**（insta） | 渲染出的技能文本进快照，改一个字都看得见 |
| **基准回归** | 改技能 / 提示词后，用基准语料重跑生成，逐篇对照信息密度、证据落点、章节职责、语气有没有回退 |
| **触发纪律评估** | 记录 `read_skill` 调用，离线看"该读的读了没、不该读的读没读" |

## 7. 已拍板（原"待定"，见 `README.md §3`）

1. **「名台词与名场面」章**已定成契约（从实例反推）：两类写在同一个列表里、靠行首区分（**台词**以 `「` 开头、原文与译文**行内对照**；**场面**以 `**名场面**：` 或 `**<场景名>**：` 开头）；**一条一行、每条都要能指到出处**（漫画/小说给卷或章、剧集/动画给话或集、电影给场景名）；**题记用过的那处不重复**；只写场面时章首加一行 `> 说明`。契约写在 `wiki-skeleton` §2。
2. **技能 `name` 用动名词短语**（如 `writing-wiki` / `checking-facts`），承载"技能 = 动作"的语义。**已定的 14 个技能名在 M4 落地时一并改名并更新 L0 目录与评测用例。**
3. **技能允许用户"可编辑"，不做分享/市场**（单用户场景）。
4. **「可机械校验」的边界**：按 `prompts.md §3` 的 13 条清单**冻结**；跑起来后只允许**从技能往质量门搬**（更严），不允许反向塞回技能。
5. **触发纪律的验收标准**：给定任务的"应读技能集合"，`read_skill` 记录须**命中全部应读项且不含应禁项**；连续两个评测轮次达成即算合格（记录进 `eval-cases.md`）。
6. **影视 / 书籍的基准语料缺口**已补（`影视/` 6 篇、`书籍/` 6 篇）。
