# Atlas v2 · 提示词与质量门契约

> **提示词怎么组装、质量门查什么——这份文档是唯一契约。**
> **关联**：AI 能力面见 `ai.md`；技能正文写法见 `skills.md`；护栏见 `behavior-notes.md §3 §6`；工具 description 归 `tools.md`。
> **纪律**：**能机械校验的规则，一律进质量门（代码），不写进提示词/技能**（`behavior-notes.md §0`）。

---

## 1. 提示词 = 分段组装

系统提示是 `section{name, order, text}` 的有序集合（v1 `run/prompt.go` 的做法，保留）：

- `name` 是唯一键，也是**替换槽位**（同名即覆盖）；
- `order` 取自中心表，**编号稀疏**（10, 20, 30…），插新段不必重排；
- `text` 是函数，拿得到运行时状态，**工具不在场就返回空串**——段自动跟着工具面走。

### 1.1 分段表（顺序即优先级）

| order | name | 内容 | 什么时候为空 |
|---|---|---|---|
| 10 | `identity` | 我是谁（馆员 Atlas）、职责、语气 | 永不为空 |
| 20 | `intent` | 本次任务框定（`This task` 段的执行偏向） | 有意图才渲染 |
| 30 | `tools` | 工具面说明（**可用的写工具规则**） | 无写工具时为空 |
| 40 | `session_memory` | 会话记忆摘要（压缩后的） | 无压缩时为空 |
| 50 | `probe` | 探查指引（先读索引/技能再动笔） | — |
| 60 | `research` | 联网研究指引 | 联网关时为空 |
| 70 | `context_window` | 窗口/预算数字（**从代码注入**） | 永不为空 |
| 80 | `doc_mode` | 阅读/编辑态约束 | 永不为空 |
| 90 | `skills` | **只渲染 L0 目录**（name + description） | 无技能时为空 |
| 100 | `closing` | 收尾/自检要求 | 永不为空 |
| 110 | `language` | 输出语言 | 永不为空 |

### 1.2 三条内容纪律

1. **一个事实只有一个 owner**：工具怎么用 → 工具 `description`；跨工具习惯 → 提示词段；身份 → `identity` 段。**写两处必然漂移。**
2. **每条规则配边界**：不说"用 edit"，说"用 edit 改一句，别为一句重写整章"；既说何时用，也说何时用不对。
3. **数字与状态从代码注入，不手抄**：`contextWindow` / 检索预算 / 压缩比例 / 管理员显示名。

### 1.3 v1 → v2 的一处修改

**技能段只渲染 L0 目录**（v1 把 `SKILL.md` + `core.md` + `media-*.md` 每个工单都塞进 system，导致噪音 / 过拟合 / 耦合）。正文由模型 `read_skill` 按需读。

## 2. 结构化产出语法

### 2.1 写作工单：FILE / REVIEW 块（借 llm_wiki）

写作 run 的模型产出是**结构化块**，不是自由散文：

```
---FILE: docs/<node-path>.md---
（完整正文，含需要的围栏语法）
---END FILE---

---REVIEW: duplicate | 标题---
描述
OPTIONS: 建档 | 关联 | 合并 | 研究 | 忽略
PAGES: ...
SEARCH: query1 | query2 | query3
---END REVIEW---
```

**解析纪律**（照 llm_wiki）：
- 有**严格解析器** + **截断修复**（半截 FILE 块要能识别并触发一次修复生成）；
- **兜底**：关键产物（如系列主文的目录骨架）即使模型漏了，宿主用确定路径补上；
- **REVIEW 动作只允许枚举值**（防模型凭空发明操作），动作集 = `建档 / 关联 / 合并 / 研究 / 忽略`（`ai.md §9`）。

> **注意**：Atlas 的主产出是"一个节点一篇正文"，所以多数写作工单其实是**工具调用式**（`write_content` / `patch_section`）而非 FILE 块。FILE/REVIEW 语法主要用于**一次产出多篇**的场景（如分析步批量建议建档、系列主文 + 子条目）。

### 2.2 分析步（两步式的第一步）

- **便宜档**、产出**结构化 JSON / 分节文本**（不是给你看的散文，是喂第二步的）；
- 覆盖：这是什么（作品/版本/载体判定）· 与库里哪些节点有关（候选+依据）· 与现有内容**矛不矛盾** · 建议怎么建（枚举动作、**不动库**）。
- **何时跳过**：只有"补一章/改一段"这类小任务跳过；整篇必走。

---

### 2.3 写作工单的落地流程（对齐 Game_Wiki 的产出方式）

> 参照 `/root/Game_Wiki/WRITING-BRIEF.md`（它就是用这套技能产出 36 篇成品的方式）。V2 的写正文工单按这个形状实现：

1. **读规范**：`wiki-write` + `wiki-skeleton` + 该介质的一个 `media-*` +（要写题记则 `epigraph`）+ 按需 `fact-check` / `prose-style` / `multi-source` / `index-fields`。
2. **联网检索（必做）**：优先官方 / 专业数据库 / 权威媒体；覆盖身份、版本关系、设定、剧情（写到结局）、玩法、评价、题记素材。**边查边记事实账本**（`断言 | 来源 | 已核实/冲突/待核实`）。
   - ⚠️ **媒体库里的年份常是"该平台再发行年"**——首发日期一律以检索为准（GameAtlas 实测）。
3. **按骨架写作**：标题 `# 作品名（介质）Wiki` → `> 说明` 行 → `:::epigraph` → `## 1`–`## 7`（+可选第 8 章 + 一句话总结 + 参考资料）。章名按介质替换。
4. **落盘 + 回报**：写入目标节点；回报必须含 **① 字数 ② 实际章节结构 ③ 待核实清单 ④ 题记用了哪一式与出处 ⑤ 关键来源**。
5. 质量门（§3）在落盘前跑；不过 → 留草稿 + 一次纠错。

> **长度**：服从信息量，按基准密度写（游戏侧基准约 **7000–12000 汉字**）。

## 3. 质量门（代码，机械项）

> **机械项一律由代码查，不写在提示词里。** 技能怎么改都不影响它——这是"把规则从提示词搬到代码"的收益。

| # | 检查项 | 判据 |
|---|---|---|
| 1 | 标题 | 以 `Wiki` 结尾；需要消歧时有 `（载体 / 年份）` 限定 |
| 2 | 题记 | `:::epigraph` **有且仅有一个**；**块内无空行**（有空行 = 段级排布，应逐行交替） |
| 3 | 章节 | `## 1.`–`## 7.` 齐全、编号连续无空号；无 `## 引言`（这个概念从未在任何一篇里出现过） |
| 4 | 章名 | 按介质三档替换（影视 = 叙事与影像特色 / 图书 = 创作特色 / 游戏 = 玩法与结构特色） |
| 5 | 第 6 章末节 | 是关系简述 |
| 6 | 说明行 | 有 `>` 说明行（整理范围 / 来源 / 剧透 / 检索时间） |
| 7 | 字段行 | 一行一个字段、值是纯值（无判断句） |
| 8 | 缺口 | 只能是 `待核实` 或整行删除（禁"据说 / 广受好评"这类糊弄） |
| 9 | 参考资料 | 条数下限；**每条引用指向存在的节点**（v1 查不了这个） |
| 10 | 字数 | 全篇字数下限 |
| 11 | 来源一致性 | 正文若提到"来源/版本"，与链和反哺状态一致（失效链要在正文交代） |
| 12 | 第 8 章（若存在） | 一条一行、每条能指到出处、**题记那处不重复** |
| 13 | 禁用表达 | 套话黑名单（"神作 / 天花板 / 据说"等） |

> ⚠️ **第 12 条不能纯机械判**：实测里 `「…」；…` 既可能是"一个场景里的两句"（合规），也可能是"两个场景挤在一行"（违规）——判据是**"读者会不会把它当一件事去搜"**。质量门最多做**提醒**（如：场面项内含 `；` 就标出来让人看一眼），**别把它做成硬失败**。

> **规范形**：所有正文入口过 `domain::text::normalize_markdown`（丢孤立 `<br />`、连续空行折一个、总以换行结尾）。

### 3.1 不过质量门怎么办

1. 留草稿；
2. 把问题**回给模型一次**纠错机会；
3. 仍不过 → **留草稿待人工**（v1 是"标 draft + 提醒"，保留这个语义）。

## 4. 技能段的渲染

- **L0 目录常驻**：每个技能一行 = `name` · 一句话 `description`（含**何时用 / 何时不用**）。
- **正文按需**：模型自己 `read_skill(name, section?)`；用户在对话输入框显式加载 Skill 时，正文直接进入上下文，并贯穿研究、骨架、生成三个阶段。
- **资源层**：技能里写 `sample:<文件名>` 指向 `skills/atlas/references/samples/`（18 篇基准）；**必须写明"只读哪一节、不要整篇照抄"**。
- **引用只一层**：技能之间避免 A→B→C 链式引用（模型可能只读到一部分）。

（技能正文的写法纪律见 `skills.md §3`。）

---

## 5. golden 快照与测试

- **稳定文本用 golden 快照钉住**：改了提示词快照就红；有意改动用 `UPDATE_GOLDEN=1` 重新生成（v1 的 `internal/run/testdata/system_prompt_*.golden.md`）。
- **段渲染进快照**：`insta` 快照测试覆盖每个 `section` 的渲染结果（含"工具不在场返回空串"的情形）。
- **技能文本进快照**：改一个字都看得见（`skills.md §5`）。
- **触发纪律评估**：记录 `read_skill` 调用，离线评估"该读的读了没、不该读的读没读"（`eval-cases.md`）。
