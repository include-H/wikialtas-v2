# 外部参考：如何写好一个 Skill（TRAE 官方最佳实践）

> 来源：https://docs.trae.cn/ide_best-practice-for-how-to-write-a-good-skill （2026-10 抓取，正文结构照录，示例代码略作压缩）
> 用途：`docs/skills.md` 的外部参照。末尾有"我们的取舍"——照录 ≠ 全采。

## 定义

一个 Skill 是一份清晰、严谨、可执行的指令文档，用于明确告诉模型——在什么条件下（**When**），按照哪些步骤（**How**），产出什么结果（**What**）。

### 三个常见认知误区

1. **Skill ≠ 一段 Prompt**。Skill 是可长期复用、输入输出明确的能力模块，强调稳定、确定、易工程化维护；Prompt 偏向临时性、探索性。
2. **Skill 不是写给人看的文档**。目标是下达指令，不是解释原理；`SKILL.md` 用模型可解析的结构化语言，明确约束行为边界与 When / How / What。
3. **Skill 越复杂 ≠ 越强大**。模型的推理与决策成本显著；职责单一、边界清晰的 Skill 更容易在正确时机被选中。上下文是有限且宝贵的公共资源——**每个被加载的 Skill 都在竞争上下文，因此以最小必要信息为目标**。

## 设计标准与原则

### 精准的元数据

| 字段 | 规范 | 好 / 坏例子 |
|---|---|---|
| `name` | 简洁唯一；小写字母、数字、连字符；**推荐动名词**；≤64 字符 | ✅ `running-tests` / `deploy-microservice` / `database-migration`；❌ `test-helper`（语义模糊）、`data-skill-v2`（含版本）、`deployService`（命名不规范） |
| `description` | **第三人称**（从模型视角描述）；**包含核心功能与触发时机的关键词**；≤1024 字符 | ✅ "Review code for quality, correctness, and maintainability. Use when evaluating pull requests, refactoring…"；❌ "I can help you review code"（第一人称）、"Helps with code review"（缺触发时机） |

### 指导方式的自由度分级

| 自由度 | 适用场景 | 指导方式 |
|---|---|---|
| **高** | 存在多种有效方法；决策依赖上下文 | **给原则**（启发式策略）。例：代码审查"先看安全性，再看可读性" |
| **中** | 存在首选模式；允许变通；行为受配置影响 | **给模板/伪代码**（框架）。例：报告生成"摘要-分析-建议"结构 |
| **低** | 操作脆弱易错；一致性至关重要；**必须遵循特定序列** | **给可执行脚本**（代码）。例：数据库迁移按固定顺序执行脚本 |

### 五个核心标准

1. **边界明确**。模型最容易犯的错不是"不知道怎么做"，而是"**不知道什么时候该做**"。必须同时写正向与负向条件：
   ```
   Use this skill when: 用户意图是触发 CI/CD 执行单元测试；PR 状态为"待合并"需要自动检查。
   Do NOT use this skill when: 用户只是查看测试报告；PR 只改文档或注释。
   ```
2. **输入输出结构化**。用类似函数签名的方式定义 Input / Output（字段 + 类型 + 含义），避免模糊描述。
   ```
   Input:  prId: string   # PR 编号
           runTests: boolean
   Output: success: boolean
           testReport?: object[]
           errorMessage?: string   # 失败时返回
   ```
3. **步骤明确、可执行**。核心是"步骤"，必须是**指令式、具体动作**，不是概括描述（❌"检查 PR，运行测试，然后更新状态"）。
4. **失败策略完备**。模型失败时容易自由发挥 → 必须显式定义失败路径：
   ```
   On Failure:
   - 校验失败：返回 400，附具体错误信息。
   - 执行失败：自动重试一次，仍失败则返回"单元测试未通过，请检查日志"。
   - 服务不可用：最多重试 3 次，仍失败则记录日志并通知管理员。
   ```
5. **职责绝对单一**。一个 Skill 对应一个核心动作动词；❌ 一个技能同时做"跑测试 + 更新状态 + 发通知 + lint"。

## 让 Skill 可维护与可扩展

### 渐进式披露

`SKILL.md` 是**入口和导航**，不是包罗万象的大文件；详细参考资料、示例、脚本拆成独立文件，按需流动。

- **保持 SKILL.md 简洁**：主体尽量 ≤ **500 行**，只含必要信息。
- **避免深度嵌套**：引用文件最好直接由 `SKILL.md` 链接，**保持一层引用深度**，避免链式引用（A → B → C），否则模型可能只读到一部分。
- **为长文件加目录**：超过 **100 行**的参考文件，顶部加 TOC。

### 工作流与反馈闭环

对多步骤、中间结果影响最终质量的任务，只给最终目标不够：要显式定义**工作流 + 检查清单**，并在关键节点建立"**验证 → 修正 → 再验证**"的闭环。

分析类任务示例：
```
## 技术方案评估工作流（每步完成后显式标记状态）
- Step 1：明确业务目标与技术约束（性能、成本、时限）
- Step 2：列出所有可行方案
- Step 3：从复杂度、可维护性、风险逐一评估
- Step 4：对关键差异点对比分析；(反馈闭环) 信息不足 → 回 Step 2 或 3
- Step 5：给出结论与取舍理由；(反馈闭环) 结论撑不住目标 → 重审 Step 1 前提
```

代码类任务用"计划 → 验证 → 执行"（示例：依赖版本升级：Plan 识别依赖与 Breaking Changes → Plan 改配置并标注受影响模块 → **Validate** 跑依赖冲突检查与静态构建 →(闭环) 失败回退 Step 2 → Execute 安装并跑全测 → **Validate** 检查回归 →(闭环) 有问题则回滚并记录风险）。

### 可执行脚本的加固

脚本的健壮性优先于代码的巧妙性：**Skill 不理解你的代码逻辑，只感知输入与输出**。一旦脚本行为不可预测，模型只能猜。

- **显式处理错误，别让模型猜**：捕获常见异常（文件缺失、权限不足、配置错误），每类错误返回**清晰原因 + 下一步建议**。
  ```
  ERROR: Config file not found: ./deploy.yaml
  HINT: 请检查路径，或运行 init-config.sh 生成默认配置。
  ```
- **输出自解释的日志与验证结果**：成功路径与失败路径都要有明确输出；验证类脚本要**列出通过项与失败项**。
  ```
  CHECK FAILED: Node.js version mismatch
  - Required: >= 18.0.0 / - Detected: 16.14.0
  VALID OPTIONS: 1. 升级 Node.js  2. 切换到兼容的构建镜像
  ```
- **避免魔法数字**：影响行为的数值要可解释、可覆盖。
  ```
  TIMEOUT_SECONDS = 30   # 服务启动通常 10–20s 内完成，故给 30s
  ```

## 构建与迭代流程：评测驱动、失败优先

**评测不是事后的验证环节，而是 Skill 设计的前提**；Skill 不是基于假设的规则集合，而是针对已暴露问题的最小化解决方案。

1. **先建"无 Skill"基线，识别真实问题**：先不用 Skill 直接让模型做任务，记录——哪些情况表现不稳定/不可复现、哪些输入引发歧义、模型是否在错误时机"主动帮忙"。这些失败点就是评测用例的来源。
2. **失败优先，先定义评测用例**：写 3–5 个**具体、可复现**的用例，每个明确"通过/失败"判定标准，**优先覆盖最易误用的场景**。（评测是约束，Skill 是落地实现；没有评测约束的 Skill 是在放大不确定性。）
3. **写最小化 Skill，明确最短成功路径**：只写刚好能过当前评测的规则集合；把评测中识别的失败场景**显式写进 Skill** 作为第一层防护；保持职责单一。
4. **补边界条件与结构化示例**：补充更多边界场景与行为约束、明确 Input/Output、补关键示例。**核心原则：所有新增规则都要对应新增或已有的评测用例**，避免无评测支撑地复杂化。
5. **评测回归与持续迭代**：任何修改都要过已有评测；**若评测未通过，优先简化 Skill，而不是盲目叠加新规则**；持续对比"无 Skill 基线"与"当前 Skill"的表现。
6. **结合真实使用路径校准**：观察是否有**非预期误触发**、是否**遗漏关键参考文件/上下文**、是否**反复读取某一段形成隐性依赖**；这些都要作为新的评测输入回到 Step 2。

## 用 AI 创建与迭代 Skill

阶段一（初次创建）：让 AI **直接执行真实任务**（追问、走偏、修正 = 一次隐式评测）→ 引导 **结构化复盘**（成功步骤 / 不确定性与失败点 / 可抽象的固定流程与判断逻辑 / 该流程的适用与不适用场景）→ 按规范生成 `SKILL.md` 初稿 → **人工只审"边界是否合理、步骤是否可执行"** → 入库。

阶段二（持续迭代）：对齐偏差来源（问题出自 **When / What / How** 哪一部分）→ 直接改 `SKILL.md` 并**验证回归**（不破坏黄金路径 + 新错误场景已被覆盖）。

## 附录：反模式检查清单

| 反模式 | 原因 | 正 / 误 |
|---|---|---|
| Windows 风格路径 | 跨平台兼容性差 | ✅ `configs/deploy.yaml`；❌ `configs\deploy.yaml` |
| **提供过多选择** | 过多选项令模型困惑、增加决策成本；**存在多个选项时必须指明一个"默认路径"** | ✅ "默认使用 PostgreSQL；仅当客户已有 MySQL 环境时才用 MySQL"；❌ "你可以用 PostgreSQL，或者 MySQL，或者 SQLite，或者 Oracle…" |
| **包含时效性信息** | 信息容易过期，导致 Skill 不可用 | ✅ 旧配置移入 `deprecated/` 并注明"不再推荐"；❌ "如果在 2025 年 8 月之前，请使用旧 API" |
| 术语不一致 | 增加理解成本，降低可用性 | ✅ 始终用 "Service Endpoint"；❌ 混用 "Service Endpoint" / "API URL" / "Endpoint Path" |

## 我们的取舍（对照 `docs/skills.md`）

**已经一致、不必改**：边界要写正向+负向（我们的 frontmatter `when` / `when_not`，即它的 `Use/Do NOT use`）；渐进式披露（我们的 L0→L1→L2→L3）；SKILL.md 简洁；示例与参考拆文件；术语要一致；工具/脚本的失败输出要可读且给下一步（我们的"截断必须说话"）。

**要采纳**（已并入 `docs/skills.md` §3 与 §5）：

1. **失败路径（On Failure）** —— 每个技能都要写"失败/不适用时怎么办"，别让模型自由发挥。
2. **结构化 Input/Output** —— 有明确产出物的技能（`analyze` / `qa` / `revise`）用函数签名式定义 Input/Output。
3. **默认路径** —— 存在多种做法时必须指定默认 + 例外条件；禁止罗列等价选项。
4. **无时效性信息** —— 技能里不写日期/版本/"某年之前的做法"。
5. **长度与引用深度** —— 技能正文 ≤500 行；**技能之间引用只一层**，避免 A→B→C；>100 行的参考文件加 TOC。
6. **自检带闭环** —— 检查项要配"不达标回哪一步"，不是只列清单。
7. **评测用例先行 + 无 Skill 基线** —— 改技能前先有可复现用例（含误触发/失败场景），并保留"不给技能"的对照；**评测不过优先简化，而不是叠加规则**。
8. **自由度分级** —— 脆弱/要求一致/必须按序列的环节给固定契约或脚本（并尽量落到质量门）；存在多种合理做法时只给原则。

**不采**：把 Skill 当成"可有可无的工程模块"的那套目录/脚本组织方式（我们 v2 的技能是**写作规范**，不是执行脚本；我们的"脚本层"是宿主代码与质量门）。

**我们比它多的部分**（它没有）：五条反过拟合纪律（特判 / 凭空禁忌 / 单实例推类别 / 例子当模板 / 清单漏项）；**基准语料（6 篇）+ 双向对齐**；**机械项搬到质量门（代码）**；**维护者元信息与运行时指令的分界**。
